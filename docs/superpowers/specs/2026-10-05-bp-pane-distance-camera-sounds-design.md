# Break the Pane — Custom Pane Distance, Camera Hold, Sounds — Design

Date: 2026-10-05
Status: approved (user answered three scoping questions; design approved in chat)

## Problem

Three user-requested changes to Break the Pane:

1. **Fixed pane distance.** The pane plane sits at `PLANE_FRACTION = 0.20` of the target distance (28 m @ 140 m; retuned from 0.25 on 2026-10-01). The player cannot move it closer or farther to vary the challenge.
2. **Camera engages too early.** The shared follow-cam engages ~1.0 s after launch (or earlier if the ball climbs out of frame) — often at or before the pane crossing, so the player misses watching the pane break from the initial view.
3. **No feedback sounds.** The app has zero audio infrastructure. The user wants a glass-break sound when a pane cell breaks, a success ding when the ball finishes on the green, and a fail sound when it misses.

## Decisions (user-confirmed)

| # | Topic | Decision |
|---|-------|----------|
| 1 | Pane-distance control | **"Custom pane distance" toggle** (default OFF = today's 20%-of-target behavior). When ON: slider in meters, range **10%–50% of target**, 1 m steps, defaults to 20% of target when toggled on. |
| 2 | Camera after crossing | Hold the static player view until the ball crosses the pane plane, **then the follow-cam engages with its normal blend** for the rest of flight and rollout. |
| 3 | Sounds | **Bundled sound files** (`res/raw`) played via `SoundPool`, plus a **Sounds on/off toggle in Settings** (default ON). Glass = at pane-crossing playback moment; ding = ball rests on green; fail = ball rests off green. |

## Design

### 1. Pane-distance slider (setup)

- `GameSetupScreen` (`GamesScreen.kt:146`) gains an optional content slot rendered with the existing controls; Target Practice passes nothing and is unchanged.
- `BreakPaneSetup` (`GamesScreen.kt:141`) owns the new state: toggle (default OFF) + pane-distance slider (visible only when ON). `onStart` grows to `(paneDistanceM: Double?, targetM: Double, difficulty: Difficulty) -> Unit`; the `SETUP_BP` branch (`GamesScreen.kt:85-96`) threads it into `breakPane.start(...)`.
- `BreakThePaneGame.start(targetM, difficulty, paneDistanceM: Double? = null)` (`BreakThePaneGame.kt:65`) passes the override to `PaneGeom`.
- `PaneGeom(targetM, planeDistanceM: Double? = null)` (`PaneGeom.kt:20`):
  - `planeYM = planeDistanceM ?: PLANE_FRACTION * targetM`
  - middle-row anchor reuses the existing API with the *effective* fraction: `zRefM = ReferenceTrajectory.paneCrossingHeightM(targetM, planeYM / targetM)` — no new trajectory function needed; the stock trajectory is deterministic per target.
  - **Cell sizes stay % of target** (`cellHM = 0.016·targetM`, `cellWM = 0.020·targetM`): the pane keeps its physical size; only its distance changes. Difficulty still controls green radius only.
- At a 50 m target the slider spans 5–25 m — valid; at 350 m, 35–175 m.
- If the target distance changes while the custom toggle is ON, the pane value clamps into [10%, 50%] of the new target; toggling OFF→ON re-seeds the slider at 20% of the current target.
- **Non-goal:** persisting pane distance in `game_results` (would force Room v4 for no expressed need). History rows continue to show game type + difficulty as today.

### 2. Camera hold until pane crossing (playback)

- `FollowCam.cameraAt(...)` (`range/FollowCam.kt:134`) gains an optional `holdUntilSec: Double? = null` parameter. When non-null, the engage time becomes `max(normalEngageT, holdUntilSec)`; blend, chase, descent, landing hold, and snap-back are untouched. Pure JVM logic, unit-testable.
- `BreakPanePlay` (`BreakPanePlay.kt:82-89`) computes the hold from the pane-crossing playback fraction that already exists for the intersection-dot reveal: `holdUntilSec ≈ PaneIntersection.mark(...).revealFraction` mapped into the same time base `cameraAt` uses for `engageT` (exact mapping pinned in the implementation plan from `FollowCam` internals; `PaneRawConsistencyTest` already proves drawn==scored crossing consistency).
- Shots that never cross the plane (duffs) have no crossing fraction → camera behaves exactly as today. Target Practice passes no hold → unchanged.
- Effect: STATIC player view through launch and the pane break → normal 1.4 s blend → chase → rollout → snap-back.

### 3. Sounds

- **Assets:** three small files in `app/src/main/res/raw/`: `pane_glass_break`, `pane_success_ding`, `pane_fail` (OGG or WAV, total well under 1 MB). Sourcing decided in the implementation plan: CC0 sound pack if cleanly downloadable, otherwise generated by a small committed script. No network dependency at app runtime.
- **New thin wrapper** `app/src/main/kotlin/com/hpsmiles/golfsim/audio/GameAudio.kt`: `SoundPool` with `USAGE_GAME`, 3 max streams; no-ops until clips finish loading; `enabled` flag; `release()` on disposal. Owned by `AppRoot` (remembered), passed down through `GamesScreen` → `BreakPanePlay`. Pure trigger logic stays out of this class.
- **Settings toggle:** new **Sounds** switch in `SettingsScreen`, default ON, persisted via the app's existing settings mechanism; bound to `GameAudio.enabled`.
- **Trigger semantics** (event-based, so 1x–4x playback speed stays in sync; audio itself never pitched):
  - **Glass break** — fires the first time playback reaches the crossing fraction of a shot that *breaks a cell* (crossed an unbroken cell this shot). Replays of the same shot re-trigger it.
  - **Ding** — ball rests on the green (including shots that crossed an already-broken cell and still finished on green: ding, but no glass).
  - **Fail** — ball rests off the green.
  - Ding/fail fire at ball rest — the same playback moment the result overlay unlocks.
- **Pure cue logic:** tiny JVM-testable `PaneSoundCues` object decides trigger moments (crossing threshold reached / rest reached / trigger-once per playback) given playback state; `BreakPanePlay`'s playback loop calls it and invokes `GameAudio`.

### Tidy-ups included

- `GamesScreen.kt:68` picker blurb still says "floating at 25% of the target" → update copy to reflect auto/custom behavior.
- `ReferenceTrajectory.paneCrossingHeightM` default param `planeFraction = 0.25` (`ReferenceTrajectory.kt:45`) → align to 0.20 (harmless today — `PaneGeom` passes explicitly — but stale).

## Testing & verification

- **JVM (pattern: existing pure tests in `app/src/test/.../games/`, run via `:app:testDebugUnitTest`):**
  - `PaneGeomTest`: override honored (`planeYM` == custom distance); 10%/50% bounds; middle-row anchor at effective fraction.
  - `BreakThePaneGameTest`: `start` with override via the existing simulator seam; outcome logic unchanged at custom distances.
  - `BreakPaneReachabilityTest`: real-engine probes at 10% and 50% of 140 m (middle row anchored to stock trajectory should stay reachable by construction).
  - `FollowCamTest`: with `holdUntilSec`, camera stays STATIC before the hold and engages with normal blend after; null hold = current behavior.
  - `PaneSoundCuesTest`: crossing trigger-once, rest triggers, replay re-trigger semantics.
- **Build:** `.\gradlew.bat build` green (JDK env var per repo convention).
- **Device:** `:app:installDebug` on the tablet; verify slider (auto + custom), camera hold at several pane distances, all three sounds incl. replays and 4x speed, Settings toggle silences audio.

## Risks / mitigations

- **SoundPool async load** → no-op until loaded; sounds never crash or block playback.
- **Glass-break asset quality** → try CC0 pack first; synthesized fallback acceptable; asset swap is a drop-in `res/raw` change.
- **Extreme pane distances** (10% of 50 m = 5 m) → reachability test + device check; middle-row anchor keeps the stock shot on-target by construction.
- **Time-base mismatch** between `revealFraction` and `engageT` → pinned in the plan by reading `FollowCam` internals; guarded by a JVM test.

## Non-goals

- Persisting pane distance in `game_results` (no Room v4).
- Sounds for Target Practice or the range.
- Volume slider or per-game sound settings (single global toggle).
- Any network/cloud dependency (hard architectural boundary).
